Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

Employee-data command execution and saving are shown in the transaction diagram.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, EmployeeListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

A few small classes keep the logic of the UI out of the JavaFX classes. CommandBox keeps a CommandHistory of the commands that were typed, for the ↑ and ↓ keys, and uses CommandCompleter to complete the command word for the Tab key. EmployeeCard uses DepartmentColour to give each department its colour and Initials to make the initials shown in the avatar. These four classes do not use JavaFX, so they are tested without a window.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Employee objects from the model.

Logic component

API : Logic.java

Here's a (partial) class diagram of the Logic component:

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete an employee).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. Logic saves the employee state and returns the CommandResult only after saving succeeds. Data-changing commands use the checkpoint and rollback boundary described below.

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

The Model component,

  • stores working data in a VersionedAddressBook and its UniqueEmployeeList, with immutable history snapshots and a current-state pointer.
  • stores the Employee objects selected by the current filter, such as search results, in a separate filtered list, and wraps it in a SortedList that puts the employees in the order of the current sort. Sorting only changes the comparator of this SortedList; the stored order does not change. It exposes the sorted list as an unmodifiable ObservableList<Employee> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Atomic employee-file saving

JsonAddressBookStorage retains its public API. It converts the complete model to JsonSerializableAddressBook, serializes using JsonUtil.toJsonString() and encodes UTF-8 before invoking the storage-local AtomicFileWriter.write(Path, byte[]). The generic JSON/file utilities, preferences and CSV writers are unchanged. JSON backups already use this storage class and therefore share its atomic writer.

The writer resolves the destination and inspects its supported access attributes, creates missing parent directories, then creates a uniquely named sibling .huntr-*.tmp file. It establishes and verifies restricted temporary access before writing any employee bytes, handles short writes until the entire buffer is consumed, forces the file and closes it. It then prepares and verifies final access protections and uses Files.move with ATOMIC_MOVE and REPLACE_EXISTING. It never pre-creates, truncates or deletes the destination, and never falls back to an ordinary overwrite or delete-then-move.

Successful replacement is the commit point. No fallible cleanup, attribute update or logging follows it. A handled pre-replacement failure preserves the existing destination bytes, or leaves a previously absent destination absent. Temporary-file cleanup is attempted on failure; cleanup exceptions are suppressed on the original failure. Created parent directories may remain. This is a handled-save-failure guarantee, not a crash-recovery journal or a promise of directory-entry durability after power loss.

The supported environment is a single-user application on local filesystems with atomic-replacement and required attribute capabilities. The access-protection contract is deliberately limited:

Concern Policy
POSIX temporary/new file Create with owner read/write only (0600) and verify before writing bytes. Retain the naturally assigned owner/group for a new destination.
Existing POSIX file Preserve the nine POSIX permission bits. Its owner and group must match the sibling temporary file's naturally assigned owner/group; otherwise fail.
Windows temporary/new file Before writing bytes, set and verify an owner-only access ACL granting full file access to the temporary file's creator-assigned owner principal. Retain this ACL and a clear DOS read-only flag for a new destination.
Existing Windows file Require matching ownership. Copy the same-provider access ACL's ordered entries as an opaque list and verify the copied list and owner before replacement. Do not translate principals or reconstruct inheritance.
Read-only file Reject an existing file that is not writable. Also require POSIX owner-write permission or, on Windows, an explicitly clear DOS read-only flag. Never clear destination protection.
Unsupported protection Fail before replacement if required views, compatible ownership, restricted temporary access, permission preservation or ACL round-tripping cannot be established. Actual access-denied exceptions retain their classification.

Java exposes POSIX permissions, access ACLs and DOS flags through separate views. Windows support covers same-owner, same-provider access-ACL copying only, not arbitrary security descriptors, audit ACLs or metadata unavailable through the Java view. POSIX special mode bits, extended ACLs and arbitrary extended attributes are outside the preservation contract. There is no ownership/group migration, principal remapping or cross-filesystem ACL migration, and no promise to preserve unrelated timestamps or metadata.

Path resolution is internal: configured paths exposed by storage remain unchanged. Bare filenames resolve against the working directory. Symbolic-link parents are resolved before choosing the temporary directory. A valid leaf link remains in place while its real target is replaced. A dangling leaf link is distinguished from an absent file and rejected; directory destinations are also rejected. Temporary files always share the resolved destination's parent/filesystem. Loading reads only the configured file, never orphan temporary files; startup scavenging, concurrent writers and live external editing are outside scope.

AtomicMoveNotSupportedException becomes an IOException with message Atomic replacement is not supported for this data file. and the original exception as its cause. A protection capability failure uses Cannot preserve the required file access protections.. AccessDeniedException remains an AccessDeniedException. Java makes existing-target replacement implementation-dependent even with ATOMIC_MOVE; real existing-file replacement tests must pass on each supported platform. A provider that cannot replace safely must fail; destructive fallback is not supported.

LogicManager continues saving after every successfully executed command. Its generic presentation is Could not save data due to the following error: <exception-message>. Its permission presentation is Could not save data to file <exception-message> due to insufficient permissions to write to the file or the folder. The latter substitutes AccessDeniedException.getMessage(), including any paths and additional diagnostic text. BackupCommand translates every IOException into Could not save the backup to <backup-path>. Check that you are allowed to write to that folder.. If backup creation succeeds but the automatic save fails, the backup remains and the automatic-save error is the final result, rather than the backup success message. For data-changing commands, including undo and redo, LogicManager restores the checkpoint on save failure, preserving employee records, the complete history and the effective view as well as the stored file. Read-only command view changes and completed backup/export files remain.

The pretty-printed UTF-8 schema remains an employees array containing id, name, phone, email, department, role and archived. Employee order, raw values and archive status are preserved. Missing archived loads as active; empty arrays are valid; invalid employee data and missing/null arrays are rejected; unknown properties are ignored. No history, transaction or schema-version fields are added.

The package-private AtomicFileWriter.FileOperations seam delegates to ordinary JDK operations. It exposes only temporary creation, attribute views/writability, a write/force/close handle, atomic replacement and cleanup. Writer tests inject faults there; storage tests verify serialization ordering and payloads; focused logic/backup tests verify presentation. Package-private parser/storage factory hooks isolate backup test paths without changing public constructors or command behavior. See the repository's tests/test-plan.md for coverage and release gates.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Reporting relationships and team structure

The reporting implementation is introduced in PR #110. Its developer documentation and the reporting sections in the User Guide are maintained together in PR #111. The implementation described here requires #110; the documentation PR does not add the commands itself.

Model and relationship validation

Employee stores an optional direct manager as an immutable EmployeeId. getManagerId() exposes an Optional, and withManager() returns a replacement employee while preserving all other fields, including archive status. Existing constructors create employees without managers. Employee identity still depends only on the case-insensitive employee ID; full equality and hashing also include the manager assignment.

ReportingStructure queries the complete roster, including archived employees. withCanonicalManager() resolves a supplied manager ID to the spelling stored in the roster and rejects self-reporting or a missing manager. validate() builds an ID lookup and follows manager links, tracking the current path and previously completed paths to reject cycles, missing managers and self-reporting. Every employee has at most one manager; multiple unconnected reporting trees and employees without managers are valid.

AddressBook#addEmployee, setEmployee and setEmployees validate the candidate roster before replacing stored data and canonicalise manager references. A failed validation leaves the existing roster unchanged. Removing an employee clears only their direct reports' manager assignments, including archived reports. Clearing active employees retains archived employees and clears references to managers that were removed.

The Model class diagram above shows that an employee holds an optional manager ID rather than a direct reference to another Employee. AddressBook delegates relationship checks to ReportingStructure.

The following sequence diagram shows the model update for an existing employee during manager assignment. ManagerCommand first finds the employee in the full roster and creates a replacement using withManager(). The diagram starts at ModelManager#setEmployee and shows validation before the stored roster is changed. ManagerCommand converts a relationship validation failure into a CommandException. History commits, saving and checkpoint restoration are handled separately by LogicManager, as described in Checkpoints and transaction boundary.

Parsing and command execution

AddressBookParser routes the five reporting commands to their individual parsers. These delegate to ReportingParserSupport, which rejects unknown parameters, duplicate prefixes, non-empty preambles, missing values and invalid IDs, and appends command-specific usage to parse errors. manager requires both id/ and m/; the other four commands accept only id/.

ReportingCommandSupport.find() searches the complete roster by case-insensitive ID, independently of the displayed list. ManagerCommand creates a replacement employee, resolves the manager, then calls model.setEmployee; relationship validation failures become CommandExceptions. UnassignManagerCommand replaces the employee with withManager(null), succeeding even if no manager was assigned. AddCommand and EditCommand also support m/: omitting it during an edit preserves the assignment, and an empty edit m/ removes it. An empty manager value on add or manager is rejected.

Query command Relationship selection
team The target employee, their direct manager if assigned, and their direct reports.
org All direct and indirect reports, excluding the target, using breadth-first traversal.
chain Managers from the immediate manager to the root, excluding the target.

ReportingStructure.reports() scans the roster for each visited manager; recursive queries take O(nk) time for n employees and k visited managers. chain() builds an ID lookup and follows manager links in O(n + h) time for a chain of height h. Both traversals track visited IDs. Result messages retain traversal order, while ReportingCommandSupport.show() installs a refreshable reporting-query predicate without resetting the SortedList comparator. Relationship changes, deletion, undo and redo recompute its ID membership against the current roster. Employee cards therefore stay current while preserving the current sort order, or roster order when no sort is active. These queries replace the current filter without modifying employee records. Model#updateReportingEmployeeList applies the membership predicate without the normal active-only restriction, so both messages and cards include related archived employees. Normal list and find continue to exclude archived employees.

Storage and presentation

JsonAdaptedEmployee persists the optional manager as managerId; a missing or null field means no manager, so older valid JSON files remain readable. JsonSerializableAddressBook#toModelType() converts all employees before calling AddressBook#setEmployees, allowing a manager to appear after their reports in the JSON array. Duplicate IDs and invalid relationships reject the entire file through IllegalValueException; no partial roster is loaded. Saved manager IDs use the existing manager's ID spelling.

ExportCommand writes eight CSV columns ending in archived,managerId; a blank manager ID means no assignment. ImportCommand also accepts legacy six-column files and seven-column files ending in archived. After parsing and checking IDs for duplicates, it resolves managers against the existing roster plus all imported rows and validates the complete hierarchy before changing the model. It adds employees without managers first, then sets their validated assignments, preserving CSV row order even when a manager appears later in the file. LogicManager commits the import as one history step and restores its checkpoint on execution or save failure. ImportCommandTest covers relationship round trips, forward references, legacy files and rejected relationships.

EmployeeCard and EmployeeListCard.fxml display the manager ID or Unassigned. Reporting usage is also listed by HelpCommand. ReportingCommandTest, ReportingCommandParserTest and ReportingStorageTest cover command behaviour, strict input validation and persistence; manual scenarios are provided below.

Workforce statistics

StatsCommand reads the complete roster through Model#getAddressBook() and ReadOnlyAddressBook#getEmployeeList(), then excludes archived employees. It reports the active employee count and calls appendBreakdown for department and role. Each breakdown groups by the stored field value and sorts by count descending, with ties ordered by the stored label ascending. An empty active roster shows a total of zero and (none) under each heading.

The sequence diagram below focuses on StatsCommand#execute after parsing. The command does not modify employee records, the current filter, the sort order or undo/redo history. As with other successful commands, LogicManager still saves the employee state before returning the result to the UI; that shared saving flow is outside this diagram.

Employee archiving

Employee has an immutable boolean archive status. Active and archived employees remain in the same UniqueEmployeeList, so case-insensitive ID uniqueness, editing and deletion naturally apply regardless of status. archive id/EMPLOYEE_ID and unarchive id/EMPLOYEE_ID replace the target with an otherwise identical employee whose status is changed. They reject unknown IDs and redundant status changes without modifying the model.

Both operations preserve the installed filter predicate and sort comparator. Updating the existing observable employee list lets the changed employee enter or leave the current view naturally, including empty search results and archived-only views. UnarchiveCommand adds a list hint when the restored employee is outside the current view.

ModelManager#updateFilteredEmployeeList combines normal predicates with an active-status check, so list and find never expose archived employees. list archived calls Model#showArchivedEmployees to select only archived employees in the same existing employee panel. edit preserves the target's archive status, while delete searches the complete stored list and can remove either status; session history can restore the removed record.

JsonAdaptedEmployee persists the status as archived in each employee object. A missing field deserializes as false, preserving compatibility with legacy data. ClearCommand calls Model#clearEmployees, which removes only active employees and preserves archived entries in the same list.

Delete an employee by ID

DeleteCommandParser accepts delete id/EMPLOYEE_ID with exactly one id/ parameter. It distinguishes unknown parameters, a missing parameter, a blank ID, an invalid ID format and duplicate parameters. A preamble before id/ is rejected as unexpected arguments. Parsing errors include the command usage; see the User Guide for messages and examples.

ID validation uses ParserUtil.parseEmployeeId and the existing EmployeeId rules: 1 to 20 letters, digits, hyphens or underscores, with no spaces. IDs retain their original casing and compare case-insensitively.

DeleteCommand searches model.getAddressBook().getEmployeeList() for the matching EmployeeId, so a target can be deleted even when hidden by the current filter. It deletes that stored employee and returns all their details. The filter and remaining roster order are preserved. An absent ID produces No employee with ID X was found. without usage, where X is the entered ID. This command uses the existing saving flow.

Edit an employee by ID

EditCommandParser requires exactly one id/ parameter and at least one field: n/, p/, e/, d/ or r/; the reporting implementation also accepts m/ as described above. It rejects unknown parameters, a non-empty preamble and repeated prefixes. A missing ID or unexpected preamble produces Invalid command format. followed by usage; an ID without any fields produces At least one field to edit must be provided.

ParserUtil validates the ID and supplied field values, returning the corresponding validation messages for invalid values. The parser stores validated changes in an EditEmployeeDescriptor; omitted fields keep their existing values. The ID only selects the employee and cannot be changed.

EditCommand searches model.getAddressBook().getEmployeeList() using case-insensitive EmployeeId equality, so filtered-out employees can be edited. It creates a replacement employee with the stored ID, including its original casing, and calls model.setEmployee. It then calls updateFilteredEmployeeList(PREDICATE_SHOW_ALL_EMPLOYEES) to show the full roster and returns Edited employee: followed by the updated details. An unknown ID produces No employee with ID X was found. without usage, where X is the entered ID. Successful edits use the existing saving flow.

Find employees by name

FindCommandParser removes the spaces at both ends of the arguments and splits them into keywords at any kind of space (the characters matched by [\\s\\p{Z}], which includes the non-breaking space of a web page). Empty arguments, and arguments beginning with /, produce Invalid command format. followed by the command usage. Each keyword is then checked against the existing Name validation rules; the first invalid keyword produces Invalid keyword: X followed by the keyword rules (FindCommand#MESSAGE_INVALID_KEYWORD). Otherwise, the parser creates a NameContainsKeywordsPredicate and passes it to FindCommand.

NameContainsKeywordsPredicate splits the employee's name and each keyword into words with StringUtil.getSearchWords, the same method that filter uses. Spaces and punctuation separate words, except for & and ', which stay in a word, and letter case and accents are ignored. A keyword matches when every one of its words is a whole word of the name, so Tan matches Tan, Ah Kow, Mary-Ann matches Mary-Ann O'Brien, and emile matches Émile, while Han does not match Hans. The employee matches when any keyword matches (OR semantics): find alex david matches either name, while find al does not match Alex. A keyword without any letter or digit never matches. It does not search employee IDs or other fields.

Because find and filter use the same word splitting, find Tan and filter n/Tan find the same employees.

FindCommand calls model.updateFilteredEmployeeList(predicate) to replace the current filter over the full employee list, without changing employee records. It returns the filtered list's size through Messages.getEmployeesListedOverview, using 1 employee listed! or N employees listed!. No matches is a successful search returning 0 employees listed!.

Duplicate employee detection

Employee#isSameEmployee compares employee IDs only, using case-insensitive EmployeeId equality. Employees with IDs E0001 and e0001 are duplicates even if their other details differ. Matching names or contact details with different IDs do not make employees duplicates; Employee#equals separately compares all fields.

UniqueEmployeeList enforces this identity rule for all employees regardless of archive status. An operation that would introduce duplicate IDs throws DuplicateEmployeeException. AddCommand first calls model.hasEmployee(toAdd), which therefore includes archived employees. A duplicate produces An employee with Employee ID X already exists., where X is the supplied ID, without adding the employee. Otherwise, it calls model.addEmployee; a same or similar name only adds a warning to the success message.

When loading JSON, JsonSerializableAddressBook#toModelType converts and validates every employee. Duplicate IDs, including IDs differing only in case, cause an IllegalValueException, rejecting the file rather than returning partially loaded data.

Filter employees by multiple criteria

FilterCommandParser first hides the slash in name words such as s/o and d/o, so that they are not read as prefixes, and rejects any prefix other than id/, n/, d/ and r/ with Unknown parameter. It then tokenizes the arguments and collects every value of each prefix. Text before the first prefix, or no prefix at all, produces Invalid command format. followed by the usage. Each id/ value must be a valid EmployeeId. Each n/, d/ and r/ value is a search value, not a complete name, department or role, so it is not checked against the rules for those fields. It only needs one word to search for, as given by StringUtil#getSearchWords; otherwise the parser reports The value of d/ should contain at least one letter or digit. (or n/, r/) followed by the usage. The parser passes the values to EmployeeMatchesCriteriaPredicate and returns a FilterCommand.

EmployeeMatchesCriteriaPredicate joins the criteria with AND and the values of one criterion with OR, which is why a prefix that is repeated widens the search while a new prefix narrows it:

  • An id/ value is met when it equals the employee ID. EmployeeId equality ignores letter case.
  • An n/, d/ or r/ value is met when every word of the value is a whole word of that field. Words are the lowercase runs of letters, digits, & and ' in the text, so d/Resources matches Human Resources but d/Engineer does not match Engineering. The words of a value may be in any order.
  • A criterion without values is not applied. The constructor asserts that at least one criterion has a value.

The sequence diagram below shows filter d/Sales d/Finance r/Manager, which is met by the managers who work in Sales or in Finance.

FilterCommand#execute calls model.updateFilteredEmployeeList(predicate). ModelManager installs the predicate on the FilteredList together with a check that the employee is not archived, so archived employees are never shown by filter. The command replaces the earlier predicate of find or filter instead of adding to it. It does not touch the comparator of the SortedList, so the sort order is kept. The result is the size of the displayed list, reported by Messages#getEmployeesListedOverview. A filter with no matches succeeds with 0 employees listed!. Like all successful commands, it is followed by the shared saving flow in LogicManager; the filter itself is never written to the JSON file.

Design considerations

Aspect: how several criteria and several values are combined

  • Alternative 1 (current choice): AND between different fields, and OR between repeated values of one field.
    • Pros: Both searches that HR staff ask for are possible with one command, such as filter d/Sales d/Finance r/Manager. Repeating a prefix needs no new symbol, which is important because punctuation is a word separator in a value.
    • Cons: Repeating the prefix is a little longer to type than a list such as d/Sales,Finance.
  • Alternative 2: Accept a separator inside a value, such as d/Sales,Finance.
    • Pros: Shorter to type.
    • Cons: The separator would also be a word separator in the value, so it would be ambiguous. Departments and roles may contain , themselves.

Aspect: whether a new filter narrows the current list or replaces it

  • Alternative 1 (current choice): A new filter replaces the earlier one, as find does.
    • Pros: The result depends only on the last command, so it is easy to predict. All the fields are given in one command.
    • Cons: A user who wants to narrow the current list in steps must repeat the earlier criteria.
  • Alternative 2: A new filter is applied to the list that is already shown.
    • Pros: Narrowing in steps is natural.
    • Cons: A mistake in a step can only be undone with list or undo, and find, filter and the reporting queries would need rules for how they combine.

Sort employees

The model keeps the employees in three layers: the stored UniqueEmployeeList, the FilteredList that holds the employees selected by the current predicate, and a SortedList over the FilteredList. ModelManager#getFilteredEmployeeList returns the SortedList, so the UI, and every command that reads the displayed list, sees the filtered employees in the sorted order. SortCommand therefore changes only the comparator of the SortedList through Model#updateEmployeeSortOrder. The stored order and the saved file are not changed.

SortCommandParser splits the trimmed arguments on whitespace. No argument, or more than two words, produces Invalid command format. followed by the usage. The first word is looked up with SortField#fromString and the optional second word with SortOrder#fromString. Both ignore letter case. An unknown word produces Unknown sort field: X. The field must be one of: id, name, department, role. or Unknown sort order: X. The order must be one of: asc, desc., each followed by the usage. Without a second word the order is ascending.

SortField#getComparator builds the comparator. It compares the text of the field after removing accents and ignoring letter case, and reverses that comparison for desc. Employees with the same value are then ordered by employee ID from A to Z in both orders, so the order of the list never depends on the order in which employees were added. The tie-break never applies to the ID field, because employee IDs are unique.

Because the SortedList observes the FilteredList, the list is kept in order without any further call. When an employee is added, edited or deleted, or when find or filter changes the predicate, the list is reordered automatically, and an employee whose name, department or role is edited moves to the correct position. Only ListCommand clears the comparator, through Model#resetEmployeeSortOrder, to show the stored order again. The sort order is not part of an undo/redo checkpoint and is not stored in the JSON file, so it is not remembered after HuntR is closed.

Design considerations

Aspect: where the sorted order is kept

  • Alternative 1 (current choice): A SortedList over the filtered list, with the comparator as view state.
    • Pros: Sorting does not touch the stored employees, so it needs no saving, undo or rollback. The order is kept when employees change or the filter changes, with no extra code.
    • Cons: The order is lost when HuntR is closed, and is not restored by undo.
  • Alternative 2: Sort the stored UniqueEmployeeList itself.
    • Pros: The order would be saved in the JSON file.
    • Cons: Every sort would be a change of the stored data, so it would need saving, a checkpoint for undo, and a way to get back the order in which employees were added.

CSV import and export

ImportCommand and ExportCommand extend the abstract CsvFileCommand, which holds the file path and the folder HuntR runs from. ParserUtil.parseCsvFilePath checks that the path is relative and ends in .csv, and CsvFileCommand#resolveFilePath rejects a path that leads outside that folder once symbolic links are followed. CsvUtil converts between a list of values and one CSV record, quoting values that contain commas, quotes or line breaks. CsvUtil.splitCsvRecords splits only at line endings outside quoted values, preserves embedded line endings and tracks the starting physical line of each record. parseCsvLine then validates each complete record's quote syntax.

ExportCommand writes the header in ExportCommand.CSV_HEADER, then one line per employee in the complete stored roster, including archived employees. It creates missing parent folders and replaces an existing file.

The sequence diagram below shows a successful import staff.csv. ImportCommand reads the UTF-8 text, splits it into complete records, checks the header against the three accepted column lists, and parses each non-blank record with the same ParserUtil methods as add. A record that is invalid, repeats an earlier ID or uses an existing ID stops the command with its starting physical line number, including when earlier records contain quoted line breaks. ReportingStructure.validate then checks the managers of the existing and imported employees together. Only after every check passes does the command change the model, so a failed import adds no one. It adds every employee without a manager first and then sets the managers, so a manager may appear later in the file than their reports.

Employee history and in-memory rollback

ModelManager owns a VersionedAddressBook, which extends AddressBook and inherits its ordinary equality and hash-code behavior. ModelManager equality also remains unchanged: history is not compared. Construction copies the supplied data and records exactly one initial snapshot with pointer zero. History lasts only for the session. The JVM property huntr.maxUndoHistory configures the maximum undo steps; VersionedAddressBook(initialState, maxUndoHistory) also accepts the limit explicitly. The default, -1, preserves unlimited history pending team agreement on a finite default. Non-negative values retain at most the limit plus one snapshots (including the current state); zero disables undo. Invalid values are rejected at construction. After a changed commit removes the redo tail and appends a snapshot, excess oldest states are removed and the pointer is adjusted. No-op commits never evict snapshots or discard redo. Checkpoints retain the pre-command history so a failed command can restore snapshots evicted by a tentative commit. Snapshots still share immutable employee objects; the limit bounds retained states, not bytes, and does not limit the size of the employee roster itself.

addressBookStateList contains complete immutable List<Employee> snapshots. Containers cannot be changed; immutable employee objects are shared. Every stored field, raw ID spelling, archive status and employee order is retained, including hidden records. commit() compares ordered employee values and raw ID strings against the current snapshot before removing redo states. Employee equality alone ignores ID case and is insufficient. A changed state discards the redo tail and appends one snapshot; an identical state leaves history untouched.

The model exposes commitAddressBook(), canUndoAddressBook(), canRedoAddressBook(), undoAddressBook() and redoAddressBook(). Each of add, edit, delete, clear, import, archive, unarchive, manager and unassign-manager declares HistoryAction.COMMIT through Command#getHistoryAction(). LogicManager commits once after successful command execution, before saving. Commands do not call commitAddressBook() themselves. This single declaration supplies both undo history and checkpoint/rollback protection. Import commits only after all rows have been added and the command has returned. Low-level mutations do not commit. setAddressBook() replaces working data without committing, resetting history or changing the predicate.

UndoCommand and RedoCommand check availability and move one step without committing. Snapshot data is restored directly; redo never executes a command again or reads a CSV. Both commands preserve the current effective view. Identical edits and clears with no active employees still reset to the active view and return their usual success messages. They create no entry and retain redo. Read-only and failed commands also retain redo.

Checkpoints and transaction boundary

Command#getHistoryAction() defaults to NONE; modifying commands return COMMIT, and undo/redo return NAVIGATE. Command#isDataChanging() is final and derives its result from that declaration. It means “this command may change employee data or navigate employee history.” The nine modifying commands and both history commands therefore return true even for no-ops. LogicManager parses first, captures a ModelCheckpoint for those commands, executes, commits only for COMMIT, then saves through the existing storage API. NAVIGATE never creates a snapshot. Only a successful storage return permits the result to be returned. No fallible work is added after that return.

A checkpoint copies the current employee-list container and the history container, retaining references to immutable snapshots, the pointer and the effective predicate. Capture takes O(n + h) work for n current employees and h snapshots; it does not reconstruct historical address books or revalidate employee pairs. Checkpoints remain usable after later changes, after redo-tail removal and after repeated restoration. Restoration copies back into the working containers and never changes a shared snapshot.

CommandException, AccessDeniedException, other IOException and unexpected RuntimeException during execution, tentative commits, serialization or saving cause restoration for data-changing commands. Command exceptions and runtime exceptions are rethrown; I/O failures retain their existing command-error conversion and use e.getMessage() in these exact templates:

Could not save data due to the following error: <exception-message>

Could not save data to file <exception-message> due to insufficient permissions to write to the file or the folder.

The permission substitution is not necessarily just the configured path. CommandBox retains text and styles CommandException and ParseException as errors; it clears text on success. It does not catch arbitrary runtime exceptions. Parse failures occur before checkpoint capture and before any save. Syntax validation for undo/redo rejects arguments before checking availability. See the User Guide for exact usage and boundary errors.

View and observable-list lifetime

The existing stored observable list and FilteredList instances are preserved. Checkpoints retain the installed predicate reference, treating installed predicates as stable. Restore applies it directly with filteredEmployees.setPredicate(...); routing through updateFilteredEmployeeList() would add an active-only condition and corrupt archived-only views. A zero-match search retains its predicate and can reveal a matching employee restored by undo. Historical searches are not part of snapshots. Selection, scroll position and suppression of intermediate list notifications are outside scope.

Persistence and atomic saving

All successfully executed commands still save, including read-only commands and no-ops. Read-only save failures retain existing behavior and are not checkpointed. Export/backup side effects are outside the transaction. Only the current employee state is serialized in the existing employees JSON schema; there are no history, checkpoint, command or predicate fields. Missing archived fields in older valid JSON still load as active; validation, case-insensitive ID uniqueness, invalid-file handling, paths and preferences are unchanged. CSV export uses eight columns including manager IDs; import also accepts legacy six-column and seven-column CSV and rejects header-only files.

Employee history and atomic saving share the recorded baseline 1d8b4b5eaeae6b1a102f92dd81a7befb18221ecb. The combined boundary is the writer's successful atomic replacement. Employee changes and history commits are tentative until then; a handled failure before replacement preserves file bytes and restores the checkpoint for data-changing commands. No fallible work follows replacement, so a completed disk commit cannot be reported as a failed save with memory rolled back. A failed no-op also restores its previous view and redo states. A failed new change after undo restores the original redo sequence.

Restart loads the last successfully saved state as one initial snapshot with no available undo or redo. External JSON editing while closed remains supported; live reload and concurrent writers are out of scope.

Validation and performance

ModelHistoryTest, HistoryCommandTest and HistoryTransactionTest cover history traversal, no-ops, raw IDs, checkpoints, view/list identity, import grouping, execution failures and save failures. Assertions compare ordered stored values separately from model equality. Existing parser, storage, CSV and command tests cover compatibility. The detailed matrix and recorded acceptance environment are in the repository's tests/test-plan.md.

For history performance, use the hardware conditions in Non-functional requirements. Start each of three measured sessions from the same 1,000-employee fixture. Perform 100 genuine edits while retaining exactly 1,000 employees, then time all 100 undos and all 100 redos: 600 measured history operations in total. Measure from command dispatch through saving to the first rendered UI frame showing the completed result and list update. Every operation must complete within two seconds. Record the maximum and environment; keep thresholds out of CI unit tests. Run the standalone UI acceptance harness described in tests/test-plan.md with atomic saving enabled.

Product scope

Target user profile:

  • is the sole HR administrator at a small or medium-sized company
  • has no HR team or dedicated HR software, and keeps employee records in spreadsheets or shared files
  • is the only person who maintains these records, on a single computer
  • manages records for up to a few hundred employees
  • often has to answer ad-hoc questions about individual employees, reporting lines and team sizes within minutes
  • can type fast

Value proposition: HuntR helps the sole HR administrator keep employee records accurate, see how staff relate to each other, such as reporting lines and team membership, and get an overall picture of the workforce, all through typed commands.

Non-Functional Requirements

The following requirements describe the intended HuntR product, including capabilities that are not yet implemented. Performance limits are acceptance targets, not measured results for the current version. Platform, packaging, storage, and display requirements incorporate the applicable course project constraints.

HuntR is intended for one HR administrator managing workforce records locally. Shared access to the same data by different users, including taking turns on a shared installation, is outside the supported usage.

  1. NFR-01: Platform compatibility. HuntR must launch and support its employee-management commands on Windows, Linux, and macOS with Java 25 installed, without requiring another Java version. Verify the same release on each operating system by adding, listing, finding, and deleting an employee, then exiting and relaunching.

  2. NFR-02: Portable distribution. HuntR must be distributed as a single executable JAR containing its application dependencies and resources. With Java 25 already installed, a user must be able to copy the JAR into a writable folder and launch it using java -jar huntr.jar, without an installer or separate library installation.

  3. NFR-03: Offline operation. Adding, listing, finding, deleting, saving, and reloading employee records must work with the network disconnected. These operations must not require a remote server or an online account, and HuntR must not transmit employee records over the network.

  4. NFR-04: Human-editable storage. Workforce records must be stored locally in a human-readable, human-editable JSON file, without a database management system. When the application is closed, a user must be able to edit the file in a text editor; valid changes that satisfy the employee field and uniqueness constraints must appear on the next launch. When launched from the JAR's folder, the default file is data/addressbook.json in that folder.

  5. NFR-05: Capacity. HuntR must support at least 1,000 valid employee records with distinct employee IDs. Saving and reloading a dataset of this size must preserve every record and its employee ID, name, phone number, email, department, and role. This is a minimum supported capacity, not a limit on the employee ID format.

  6. NFR-06: Command response time. Each add, list, find, and delete command must display its result and finish updating the employee list within 2 seconds of pressing Enter, including any automatic save. Verify 20 executions of each command under the performance conditions below, including searches with zero matches and searches matching all employees; every execution must meet the limit.

  7. NFR-07: Startup time. HuntR must load the saved records, display the employee list, and accept command input within 5 seconds of starting the JAR process under the performance conditions below. Verify this over five separate launches; every launch must meet the limit.

  8. NFR-08: Keyboard usability. After launch, an HR administrator must be able to add an employee, list employees, find an employee, delete an employee, access help, and exit using only the keyboard. Each of add, list, find, and delete must accept its required input in one command submission, without requiring mouse interaction or a sequence of input dialogs.

  9. NFR-09: Recoverable input errors. Rejected commands with invalid syntax, invalid field values, a duplicate employee ID, or a nonexistent target employee ID must leave stored records and the displayed employee list unchanged. The application must remain open and accept the next valid command. The English error message must identify the problem and provide the expected command format or field constraint where applicable.

  10. NFR-10: Persistence reliability. A data-changing command must save its changes before reporting success. After a successful command followed by normal shutdown and relaunch, all employee records and field values must match the saved state without a manual save. Verify additions and deletions, including deletion of the last employee. If saving fails, such as because the data folder is not writable, HuntR must report the save failure instead of reporting success.

  11. NFR-11: Invalid-file handling. If the employee data file contains malformed JSON or an employee that violates the field or uniqueness constraints, HuntR must reject the whole dataset, start with an empty employee list, and record a warning in the log. It must not load only the valid entries from that file. A missing or malformed preferences file must cause HuntR to use default preferences without preventing startup.

  12. NFR-12: Display usability. At resolutions of 1920 x 1080 and higher with 100% or 125% display scaling, the command box, result display, and employee list must remain accessible, with their text readable directly or through scrolling. All functions must also remain usable at resolutions of 1280 x 720 and higher with 150% scaling. Verify each resolution/scaling combination with the application maximised, including long employee details and error messages.

Performance verification conditions: Use Java 25, a computer with at least two CPU cores and 8 GB RAM, a local SSD, and no other resource-intensive applications running. Use 1,000 valid employee records with distinct IDs and up to 100 characters in each other text field. Restore this dataset before each command trial. Record the operating system, processor, Java version, dataset, and timings with the test results. These fixture sizes do not introduce new field-validation limits.

Glossary

These definitions describe HuntR's employee-management domain. The inherited codebase still uses names such as Person and AddressBook for the underlying records and their collection.

Term Definition
AB3 AddressBook Level 3, the contact-management application from which HuntR is adapted.
Command-line interface (CLI) An interface controlled by typing text commands. In HuntR, commands are entered in the GUI's command box and submitted with Enter.
Data file The local JSON file containing workforce records. The default is data/addressbook.json, relative to the application's working directory. It is separate from the preferences file.
Data persistence Saving records to disk so that they remain available after the application closes and are restored in a later session.
Department The organisational unit to which an employee belongs, such as Engineering or Finance; supplied using d/.
Displayed index An employee's position in the currently displayed list, starting at 1. It can change when the list changes and is distinct from the employee ID. HuntR's specified delete command uses the employee ID.
Duplicate employee record A record with the same employee ID as another record. Two employees with the same name but different employee IDs are distinct records.
Employee A member of the organisation whose information the HR administrator manages in HuntR. An employee record contains an employee ID, name, phone number, email, department, and role.
Employee ID The unique identifier for an employee record: 1 to 20 letters, digits, hyphens or underscores, with no spaces, such as E0123, EMP-0042 or 2024-017. It is stored as typed and compared case-insensitively. It is supplied using id/ and distinguishes employees even when their names are identical.
Filtered employee list The subset of stored employee records currently displayed after applying search criteria. Filtering changes the view without deleting records from the workforce roster.
Graphical user interface (GUI) The application's visual interface, including the command box, result display, and employee list.
HR administrator The human resources staff member who operates HuntR to maintain the organisation's employee records; the application's target user.
JAR Java Archive: the executable package containing HuntR's application code, dependencies, and resources.
JSON JavaScript Object Notation, the text-based format used for employee data and preferences.
Keyword A space-separated search term supplied to find. It matches a whole word in an employee's name, ignoring letter case. With multiple keywords, a match on any one keyword is sufficient.
Main success scenario (MSS) The sequence of steps in a use case when the interaction succeeds without taking an error or alternative path.
Preferences file The local preferences.json file containing application settings, such as window size and position, rather than employee records.
Reporting relationship An optional link from an employee to their direct manager, identified by employee ID. Manager references must exist, and self-reporting and cycles are rejected.
Role An employee's job title, such as Software Engineer or Accountant; supplied using r/. It does not denote application access permissions.
Session One period of application use, from launch until shutdown.
Workforce records / roster The complete collection of employee records stored in HuntR, including employees not visible in the current filtered list.

Saving data

The employee data file is data/addressbook.json, relative to the folder from which java -jar huntr.jar is run. Back up this file before the following tests and restore it afterwards.

Persisting a successful change

Prerequisites: Launch HuntR and ensure employee ID SAVE-001 does not exist.

  1. Enter add id/SAVE-001 n/Save Test p/91234567 e/save@example.com d/QA r/Tester.
    Expected: HuntR reports that the employee was added and updates data/addressbook.json without requiring a separate save command.
  2. Enter exit, then run java -jar huntr.jar again.
    Expected: Employee SAVE-001 is loaded with all six fields unchanged.
  3. Enter delete id/SAVE-001, exit, and relaunch HuntR.
    Expected: Employee SAVE-001 remains deleted after relaunch.

Dealing with a missing data file

Prerequisites: Close HuntR. Move data/addressbook.json to a backup location so that the original path does not exist.

  1. Run java -jar huntr.jar.
    Expected: HuntR starts with the six sample employees instead of failing to launch.
  2. Enter list and close HuntR.
    Expected: HuntR creates a new data/addressbook.json containing the sample employees. Restore the backup after closing the app if the original data is still needed.

Dealing with a corrupted data file

Prerequisites: Close HuntR and back up data/addressbook.json. Replace its contents with text that is not valid JSON, such as { invalid json.

  1. Run java -jar huntr.jar.
    Expected: HuntR starts with an empty employee list. It does not load sample employees for a corrupted file, and the log records a warning that the data file could not be loaded.
  2. Enter list.
    Expected: HuntR remains usable, displays the empty-list guidance, and replaces the corrupted file with a valid JSON representation of the current empty roster. Close HuntR and restore the backup after the test.

Dealing with invalid employee data

Prerequisites: Close HuntR and back up data/addressbook.json. Edit one stored employee so that its ID contains an invalid character, or duplicate an employee using the same ID with different letter case.

  1. Run java -jar huntr.jar.
    Expected: HuntR rejects the entire file and starts with an empty employee list; it does not partially load valid employees. The log records a warning describing the invalid data.
  2. Close HuntR without entering a command and restore the backup.
    Expected: The original employee data is available again on the next launch.
