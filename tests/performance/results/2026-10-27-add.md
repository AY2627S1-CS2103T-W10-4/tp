# Similar-name lookup and add-command benchmark

Sample run on 2026-10-27 using Zulu Java 25.0.3 on macOS ARM64, from branch `fix/issue-199`.
The application, tests and benchmark were compiled directly with Java 25 and cached runtime dependencies.

Reproduce the workload with:

```sh
./gradlew -I tests/performance/history-performance.gradle addPerformance
```

Each scenario has 30 warmup iterations and 100 measured iterations. Fixtures contain half active and half archived
employees. Names include repeated spaces and composed/decomposed Unicode accents. `none` has no matches, `sparse`
has six matches (the first five and the final employee), and `all` matches every employee.

The isolated scan comparison uses identical rosters and checks equal match counts. The uncached path emulates
the former `normalise(existing).equalsIgnoreCase(normalise(target))` comparison. It does not run a prior application
revision or include the former unbounded warning-string construction, so this is not a full before/after add comparison.

The actual-add column runs production `AddCommand.execute` against a real `ModelManager`, including model mutation,
ID checks, reporting-structure validation and warning formatting. The added record is removed after each timed call.
Roster construction, loading, target-name construction, cleanup, history commits, JSON saving and UI rendering are
excluded. Caching moves normalisation to immutable `Name` construction, whose time and retained memory are not
measured here. No model or storage stub is used for measured adds.

In this sample, a 10,000-employee add took about 1.69–1.72 ms without persistence/UI work. Both similarity scans
remain O(N) comparisons; caching reduces repeated normalisation, not the number of roster entries visited. Name
length also affects comparison cost. Exact totals require processing matches after the five-ID preview fills.

These are single-process diagnostic averages, affected by JIT compilation, allocation, garbage collection and
workload order. Small-case timing differences are not evidence of sublinear scaling. This is not a rendered-UI
acceptance test or a statistical performance guarantee, and CI asserts no speedup ratio.

`AddCommandPerformanceTest` separately validates real-model additions on 10,000-employee rosters: no matches,
all matches (including archived records), and a sixth match at the end. It checks exact warning text, the five-ID
preview and preservation of existing records. A fourth test covers the exactly-five boundary. The generous
10-second command-only guard catches severe regressions while excluding fixture construction.
